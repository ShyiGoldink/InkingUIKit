## 2. 基线事实（核实结论）

### 2.1 六条主张的三态判定

| 条目 | 判定 | 证据 |
| - | - | - |
| 1.「基于 timeline 做」 | **部分成立** | `Timeline` 确有自定义频率订阅（`include/timeline/Timeline.h:59-79`），但唯一实例是 `WindowState` 成员（`src/window/InkingWindow.cpp:242`），**无对外访问点**；组件拿不到 |
| 2.「订阅 timeline 这种样式」 | **成立（需中转）** | 可做成场景级 `SubscribeAnimation`，语义与 `Timeline::Subscribe` 同构（累加器追赶，`Timeline.cpp:125-145`），链路仍由 `TickFrame` 驱动（`InkingWindow.cpp:911-915`） |
| 3.「图集为了合批」 | **当前不成立**（T-07 后改为"可以做到"） | 矩形 + `Fill` 走 `SDL_RenderTexture` 并 `NoteImmediateDraw()`，**明确不合批**（`src/render/InkingDraw.cpp:649-657`，注释自述"这些矩形图片不再合批"）。0.2.0 绕开批次是为了 alpha 正确性，但 T-07 探针证明**当前 SDL 的几何批 alpha 是对的** ⇒ 障碍不存在，只是还没并（§2.3 / §5 T-07） |
| 4.「小图和图集都要」 | **成立** | 两条路各自落点不同：序列帧走纹理缓存查表（键 = `ImageBytes::name`，`src/render/InkingText.cpp`），图集只需源矩形（`InkingImageFit.h` 现无 `srcRect` 字段） |
| 5.「考虑重绘」 | **成立（但归因相反）** | 重绘脏**不控制绘制**：`Render` 每帧画全部节点，脏只用于静默检测（`src/scene/InkingScene.cpp:443-482`，`kRepaintQuietFrames = 5`）。真正开销在换纹理/解码 |
| 6.「命名 `InkingSprite`」 | **成立** | 用户拍板；作为 `InkingStaticImage` 派生，静态档属性不变 |
| 7.「派生类可直接换渲染外观」 | **不成立（写任务书时踩到）** | `_renderAppearance` / `refreshRenderAppearance()` / `applyData()` / `_assetBytes` 全在 `InkingStaticImage.h:167-194` 的 **private** 段。派生类能用的只有 public `SetImageBytes()`；要"换源矩形"必须由基类新开 protected 钩子，或让 `ButtonAppearance` 带字段（见 T-03 / T-04） |
| 8.「`ImageAppearance` 这个类型存在」 | **不成立（笔误已修）** | 仓库里只有 `ButtonAppearance`（`include/button/ButtonData.h:57`）与 `PanelAppearance`（`include/panel/PanelData.h:42`），没有 `ImageAppearance` |

### 2.2 时间链路（已核实）

| 通道 | 频率 | 落点 | 收谁 | 出处 |
| - | - | - | - | - |
| `TickLogic` | 固定 50Hz | `onTick` | 动态档 | `InkingWindow.cpp:904-909` |
| `TickFrame` | 每渲染帧 | `onAnimationTick` | **所有节点** | `InkingWindow.cpp:911-915` |
| 自定义频率 | 按需 | **不存在**（本批补） | — | — |

`TickFrame` 只对活跃场景派发（`_rejected || _closed || !_active` 提前返回），
故"切走的场景动画冻结"是现成语义。

### 2.3 图片绘制三条路（合批现状）

`detail::fillShapeTextured`（`src/render/InkingDraw.cpp:605`）：

| 条件 | 走哪 | 合批 | 出处 |
| - | - | - | - |
| 矩形 + `Fit::Fill`（最常见） | `SDL_RenderTexture`，`srcRect = nullptr` | **否** | `:649-657` |
| 非矩形，或 `Cover` | `AppendTexturedGeometry` | 是（同纹理连续 N 笔 = 1 次） | `:671-677` |
| `Fit::Contain` | 设裁剪矩形 + 直接提交 | 否 | `:679-682` |

路径 1 绕开批次**原本**是为正确性：0.2.0 当时记的是"`SDL_RenderGeometry` 下纹理 alpha
不参与混合，透明区变成半透明黑"（`:630-648` 有当时的实测记录）。

> **0.6.2 T-07 复核（2026-10-27）**：在 SDL **3.4.16** 上这条**不复现**——software 与
> `direct3d11` 两个后端上，几何批的透明区 / 50% 半透明 / 放大采样与 `SDL_RenderTexture`
> **逐位相同**（数字见 §5 T-07）。所以"图集合批"的障碍不是正确性，只是这条快路还没并过去。
> 该记录保留原文，只标"在旧 SDL 上成立"。

**结论：图集的收益是纹理/解码复用 + draw call 合并**（T-08 已把这条快路并进批次，默认行为；实现与开关见 `src/render/InkingDraw.cpp` 与 `InkingBatch.h`）。

### 2.4 2026-10-28 三项需求的三态判定

| 条目 | 判定 | 证据 |
| - | - | - |
| ①「你提到的缺陷」 | **成立（两条）** | (a) 图集只能从第 0 格起：`SpriteSheet` 只有等比网格，`CellRect(index)` 把 `index` 直接当**绝对格号**（`include/image/SpriteData.h:117-136`），没有任何起点字段 ⇒ "4 行 = 4 个方向"时播不了第 1~3 行；(b) 采样模式硬编码：`InsertTexture` 里 `SDL_SetTextureScaleMode(entry.texture, SDL_SCALEMODE_LINEAR)` 且无开关（`src/render/InkingText.cpp:554`） |
| ②「加载某个资源时把整个图集**全部**加载好」 | **部分成立（一半已经是现状）** | 对**等比网格**这条路，现状**就是**"一份字节、一张纹理、N 帧只换源矩形"：图集帧的 `LoadedFrame.data` 留空 ⇒ 不逐帧拷字节（`src/image/InkingSprite.cpp` 的 `loadFrameBytes`），换帧只写 `SetRenderSourceRect` ⇒ 没有"逐帧资源"可加载。真正缺的是 (a) **帧矩形不等**（`CellRect` 只有等比算术，`SpriteData.h:117`）、(b) **一份图集里多个具名动画的查找**（`AssetLoad` 只返回字节，`include/asset/InkingAsset.h:80`，整个 `asset/` 层没有"描述符"概念） |
| ③「动画组很好实现，只要一个管理入口」 | **部分成立** | 数据（名字 → 配置 + 当前索引）确实是薄封装；缺的是**运行期换配置的入口**：`InkingSprite` 公开段只有 `Play/Pause/Stop/SeekToFrame` 与观测口（`include/image/InkingSprite.h:115-166`），`loadFrameBytes()` / `validateSheetGeometry()` 只在构造期调（`include/image/InkingSprite.cpp:128`），`_mode` 注释明写"构造时定，之后不变"（`InkingSprite.h:214`）⇒ 现在"切动画"只能重建组件（订阅全丢、z 序要重排、父级要重布局） |
| 附带核实：库内有 json 解析器吗 | **库内没有，但生成器里有一份现成的** | `include/` + `src/` 对 `JsonValue` / `ParseJson` / `nlohmann` / `rapidjson` 全部零命中；而 `tools/inkgen/Json.{h,cpp}` 有 **495 行**（头 94 + 实现 401）、只依赖 std、**零 `throw`**（返回 `{ok, value, error}`，错误带行列号、`\uXXXX` 转义齐、重复键报错），唯一使用者是 `Cxxcss.cpp`。⇒ 「运行期解析」的成本**不是写解析器**，而是①提升成 `detail/` 共享件 ②决定失败语义 ③加缓存。**原稿写的「几十 KB 代码」是错的，2026-10-28 更正。** 另一个信号：`AssetLoadText()` 公开存在、注释写着「配置 / json / shader」，但 `src/` 与 `examples/` **零调用**——运行期文本配置当初留了口子，没落地 |

| 后端 | 并批 `Linear` | 并批 `Nearest` | 单笔 `Linear` | 单笔 `Nearest` | 4× 放大同色块（并批 Nearest） |
| - | - | - | - | - | - |
| `software` | 2 色 | 2 色 | 33 色 | 2 色 | 127/256 = **49.6%** |
| `direct3d11` | 12 色 | 2 色 | 12 色 | 2 色 | 256/256 = **100%** |

d3d11 认。像素素材因此两条路都是硬边（它本来就要最近邻）；"软件后端 + 高清图平滑缩放"

## 11. 明确不做（避免反复讨论）

| 不做的事 | 原因 |
| - | - |
| 关键帧插值 / 属性动画（位移 / 缩放 / 颜色曲线） | 是"曲线 + 插值目标 + 混合"，与离散换帧是两个问题；`Timeline` 当节拍器没问题，但数据结构与组件都得另起 |
| 把 `Timeline` 实例直接暴露给组件 | 重开窗口即重建，句柄失效且撞已析构节点；场景级订阅已覆盖同一语义（§2.1 第 2 条） |
| 变速 / 倒放 / 进度条 | `fps` 是常量；需要时业务层用 `SetFps` + `SeekToFrame` 自行组合 |
| 跨场景共享播放状态 | 播放状态属于组件实例，不做全局播放器 |
| 音频与动画自动同步 | 业务用 `frameChanged` / `frameEvent` 自己挂 |
| 图集打包工具 | 美术侧自备；本版只读图集 |
| 「图集会自动合批」这一预期 | §2.3 已证：0.6.2 之前矩形 + Fill 绕开批次；合批已在 T-08 落地，开关是 `detail::SetImageBatchingEnabled` |
| 逐图采样模式（同屏混用像素素材与高清图） | 采样模式必须并进纹理缓存键，否则同名换模式会命中旧纹理；0.6.4 只做进程级开关（T-12 方案 B），真有混用需求再做 |
| 图集描述文件的运行期解析 / 热更 | **不是**「解析器太贵」（生成器里那份 495 行、可直接提升为 `detail/` 共享件），而是**时机分工**：结构（帧矩形）进 exe、字节进 assets，「换美术不用重编」已经够用。真要做，触发条件是「图集与描述一起下发（关卡包 / 皮肤包）」或「编辑器里改一格要立刻见效」——那时第一件事是**把 `Json.{h,cpp}` 提升为共享件**，而不是新写一个（T-16 方案 B / T-17） |
| TexturePacker 的帧内偏移（`spriteSourceSize` / pivot） | 要改 `PaintImage` 的绘制矩形原点；等有素材真的这么导出再做（T-14 方案 B） |
| 动画组用 N 个节点 + `SetVisible` 实现 | 绘制列表与命中表中常驻 N−1 个不可见节点，与 0.6.2 的合并收益相抵（T-18 方案 B） |
| 动作间的过渡 / 混合（crossfade） | 需要两套帧同时在场 + 权重，与"一个节点换配置"互斥；先把"切换"做对 |
| 引入第三方 json 库（nlohmann / rapidjson） | 我们已经有一份 495 行、零异常、带行列号、重复键会报的实现；第三方在这三点上都更差，且会引入新的 ABI/编译负担（T-15 把它公开就是为了替代这条路） |
