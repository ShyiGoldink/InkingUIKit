## 0. 结论（TL;DR）

五条建议全部经核实**成立**（一条的归因被修正），拆成 **5 个任务、3 个批次**。三批都不改渲染行为：

| 编号 | 任务 | 批次 | 对应条目 | 落点 | 代价 |
| - | - | - | - | - | - |
| T-01 | 把行为自检挂进 ctest | 0.8.0 | E1 / E2 | `CMakeLists.txt:365` | 低 |
| T-02 | 自检支持真后端（d3d11） | 0.8.0 | E3 / E9 | `examples/demo/selftest.cpp`（`main`） | 低 |
| T-03 | 重打 0.7.1 预编译包并走通 minimal | 0.8.1 | E4 / E6 | `tools/package.sh`、`tools/BUILD.txt` | 中 |
| T-04 | 打包的"版本号与二进制一致"护栏 | 0.8.1 | E5 | `tools/package.sh:57` | 低 |
| T-05 | 纹理字节账本（只加数，不改策略） | 0.8.2 | E7 | `src/render/InkingText.cpp:54` | 低 |

设计取向三条：

1. **证据先于功能**。这批任务几乎不改产品行为，只把"已经对了"变成"随时可验证"。现状最刺眼的不是缺功能，而是**565 项行为断言一条都不在 `ctest` 里**——`ctest` 全绿证明不了产品能用。
2. **先走通再上护栏**。T-04（打包一致性检查）必须在 T-03（真的打一次包）**之后**做：护栏的作用是锁住一条已经跑通的流程，而不是把一个从没走通的流程固化下来。
3. **统计面单独一批**。T-05 只加数字、不加策略——有了峰值字节，才谈得上定预算；先定预算再找数据就是拍脑袋（0.7.x 已经因为"没有数就定规则"返过一次工）。

## 1. 任务维护规则（本文件的写法约定）

### 1.1 每个任务必须写三段

| 段 | 要求 |
| - | - |
| **准备怎么改** | 决策与选型：做什么、走哪条路、为什么；**放弃的候选要写出来** |
| **大致改动逻辑** | 代码级顺序：改哪个文件、加哪个函数、谁调谁、哪一步不能反。不贴大段代码 |
| **与改动前对比** | 表格；**至少一行"改动后仍不变"的边界**，否则是过度承诺 |

另附 **落点**、**验收**（可断言）、**风险与回退**（至少各一条）。

### 1.2 完成即压缩（核心规则）

任务完成后，把该任务整段压缩成一行：

```
- T-01 <标题>-已完成（<YYYY-MM-DD>，<一句可验证的结论>）
```

删除「准备怎么改 / 大致改动逻辑 / 与改动前对比 / 验收 / 风险」五个细目，并把 §6.2 进度表的状态改为 `已完成`。**两处必须同改。**

### 1.3 四种状态

| 情况 | 写法 |
| - | - |
| 完成 | `- T-01 <标题>-已完成（日期，结论）` |
| 放弃 | `- T-01 <标题>-已放弃（原因；替代方案）` |
| 拆分 | `- T-01 <标题>-已拆分为 T-01a / T-01b` |
| 阻塞 | `状态：阻塞（原因）`，保留全部细目，不压缩 |

### 1.4 完成的定义（DoD）

1. 编译通过；2. 验收断言在自检 / ctest 里跑绿；3. 涉及文档同步改；4. 「与改动前对比」每行都能对上实测。

| E1 行为自检不在 ctest 里 | **成立** | `ctest -N` 只有 4 条（inkgen 校验 / 字段表 / 生成链路编译 / 静默清单对账），**没有** `inking_demo_selftest`。而它实测 565 项、耗时 **3.57 s**、`exit=0` |

| E5 打包没有版本一致性检查 | **成立** | `tools/package.sh:25` 的 `version_of()` 从 `include/inking.h` 读版本（现在是 0.7.1），二进制却取自 `BUILD_DIR="build-release"`（`:23`）。两者不比对 ⇒ 旧构建会被**静默**打成新版本号 |
| E6 `examples/minimal` 与 dist 的绑定点 | **部分成立**（我最初的判断错了） | 我一度认为 `INKING_SDK_DIR` 未定义是 bug——**不成立**：它由 `cmake/inkingConfig.cmake.in:35` 提供。真正的问题只是注释里写死 `inking-0.5.2-win64`（`examples/minimal/CMakeLists.txt:10`） |
| E7 没有纹理字节账本 | **成立** | `TextureEntry`（`InkingText.cpp:54`）只有 `width/height`；`TextCacheStats`（`InkingText.h:74`）只有计数。上限散在三处（`kMaxSvgVariants=3`、`glyphPacker{1024}`、`kMaxTextRasterCap=8`），**没有全局预算**，也没有"当前占多少字节" |

> **一条给后来者的警告**（写在这里因为下一步就会踩）：手工重编自检时漏掉 `-DINK_ISMESSAGE=1` 会让"消息队列入队 / 出队"这条**假红**（队列退化为空实现）。我第一次跑 d3d11 变体就是这么红的，一度误判成"后端差异"。`ctest` 走 CMake target 不会错，手搓命令行会。

## 7. 明确不做 / 待设计（避免反复讨论）

| 事项 | 结论 | 原因 |
| - | - | - |
| **TextBox（多行 / 多语言）** | **待需求梳理，不排期** | 方案还没定：多语言要回答"串从哪来、什么时候切"（`InkingText.h:302` 那段契约写了四条，但"预烘 vs 切时重烘"没定）。任务书的前提是方案已定——先做需求梳理，别把探索写成任务 |
| **`package.sh` 自己构建** | 不做（本批） | 会把"编译失败"与"打包失败"混成一种红，排查变贵。等 CI 真跑起来时再评估 |
| **CI 云服务（GitHub Actions 等）** | 不做（本批） | 仓库当前没有 CI 平台与 runner；T-01/T-02 已经让"本地一条 `ctest`"覆盖同一批证据。上云是搬运，不是新增证据 |
| **9-slice / portal / 逐图采样** | 继续搁置 | 理由见 `2026-10-29-scaling-and-device-pixels.md` §7 与 `2026-10-25-0.6.x-frame-animation.md` §11：都有绕法，等真有人要 |
