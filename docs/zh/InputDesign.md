## 0. 这份文档解决什么问题

一句话：**命中结果与渲染结果必须来自同一套几何真相，且一帧只算一次。**

具体拆成四条可检验的约束：

1. **每帧只判断一次**（§1）。指针状态在那里变，但"谁被指着""谁被按下"每帧只结算一次，
   不在事件到达时逐个组件问。
2. **命中与渲染共用一条 z 序**（§1、§6）。渲染顺序和命中顺序用同一个比较器，
   否则会出现"画的是 A、点到的是 B"——两边单独看都对，合起来才错。
3. **重活只在真的需要时做**（§4、§5、§10）。几何变了才重烘表；指针移动不重烘；
   颜色 / 文字 / 变换只标重绘脏。
4. **静态层的表冻结，动态层自判**（§2、§7、§11）。静态组件构造即定型 ⇒ 可以烘表查表；
   动态组件几何会自己变 ⇒ 不进表，自己判。"两档"这个划分的存在理由就是这条。

## 1. 设计目标：每帧只判断一次 + 一条层级序

**"每帧只判断一次"** 的落点是 `InkingScene::DispatchPointer()`。窗口层只负责把这一帧的
原始状态喂进来（`SetPointerState(designX, designY, down, inside)`），场景**只存不判**；
真正的判断在帧循环里的固定位置做一次。

这样做的三个直接后果：

| 后果 | 说明 |
| --- | --- |
| 一帧内的多次改动被合并 | 一帧里连续 `Resize` 三次、`ChangeZIndex` 两次，只在帧末结算一次（§5） |
| 判断顺序唯一 | 先更新捕获 → 再据此算悬停 → 最后派发；倒过来就会出现"抬起那一帧悬停还停在旧节点" |
| 回调里改结构是安全的 | 派发过程中节点可能被析构，所以每步都比一次结构代次（§8、§14） |

**"一条层级序"** 的落点是 `InkingWidget::IsAbove(a, b)`：**树序 + 兄弟内 z**——
父容器先于自己的子孙，`zIndex` 只在兄弟之间生效，同 z 时**晚注册的在上**。
规则只能有一条——跨子树、跨簇、跨溢出桶都要能统一比较，否则不同来源的候选之间无法定序。
它现在实现的是**局部层级**（A8b），但仍然是**严格全序**，所以这一条不变量没变。

`HitTable` 里候选按 z 降序填，"第一个真正包含该点的"就是最上面那个（§10.2）。
**渲染顺序与命中顺序必须共用同一个比较器**。

> 局部层级（A8b）已经落下：`IsAbove` 现在是"从根到自己的 (z, 注册序号) 序列按字典序
> 比较"，调用方一处都没改——这正是把比较器集中的理由。**还没做的是 portal**：
> 子节点无法盖住父级的兄弟，做到那一步才需要 §10.5 规则 4 的跨簇仲裁。

## 2. 三档组件（以及"档不迁移"）

| 档 | 判据 | 进不进命中表 | 收不收每帧 Tick |
| --- | --- | --- | --- |
| **静态档** `InkingStaticWidget` | 几何**构造即定型**（位置 / 尺寸 / 形状构造后不动） | 进（烘成条目） | 不收 |
| **动态档** `InkingDynamicWidget` | 几何会在运行期自己变 | 不进（表里只有一个"洞"） | 收 |
| **容器**（`InkingStaticPanel` 一族） | 子孙的几何不随容器滚动位移变化 | 子孙**不进**表（A8a） | 视档而定 |

**第 3 条（稳定编号）**：`_dynamic` 是构造时如实传进来的 `bool`，**之后不变**——
**不支持运行期在静态 / 动态之间迁移**。

理由：迁移会同时改三件事的归属——命中表的条目、每帧 Tick 的名单、标脏的消费路径。
把三者做成可切换的，等于让每个组件都背一份两档的混合状态机；而"构造时选一档"只在
一处出错（构造函数），是可断言、可 review 的。

> 因此**静态档没有几何写入口**：`Resize` / `ChangeOffset` / `ChangeSelfAnchor` /
> `ChangeTraceAnchor` 只挂在 `InkingDynamicWidget` 上。要运行期改尺寸就选动态档，
> 代价是不进命中表（命中要现问）。

## 3. 输入的三层与顺序

```
窗口层（InkingWindow::runLoop）
  ├─ ShortcutRegistry::Dispatch         ← 最先：命中快捷键就消费本帧该 Down 事件
  ├─ 指针：SetPointerState / SetPointerWheel
  ├─ 键盘：PushKeyDown / PushKeyUp / PushTextInput → 焦点节点
  ├─ 场景：DispatchPointer()            ← 每帧一次：捕获 → 悬停 → 派发
  └─ 场景：ConsumeFrameDirty()          ← 帧末：推进安静帧计数、清指针脏
```

三条纪律：

1. **快捷键先于一切**：命中即消费本帧的 `KeyDown`（`KeyboardInput::ConsumeFrameEvent`），
   但**不动跨帧的 `IsKeyDown`**——业务仍能通过状态查询看到"键是按下着的"。
2. **指针是"推"，状态是"拉"**：静态组件由场景推 `onPointerHover(bool)` / `onPointerPress(bool)`；
   动态组件不进表、不被遍历，只能在自己的 Tick 里读 `GetPointerX/Y` 自己判（§7）。
3. **滚轮是一次性量**：本帧没派发出去也照样在帧末清掉。攒到下一帧会变成
   "切场景 / 移动鼠标后莫名滚了一下"。

## 4. 标脏的触发源（只有这四类）

| 触发源 | 是否标脏 | 走哪条通道 |
| --- | --- | --- |
| 几何（position / size / 锚点） | **是** | 命中脏 + 重绘脏 |
| 可见性（hide / show） | **是** | 命中脏 + 重绘脏 |
| 层级（zindex） | **是** | 命中脏 + 重绘脏 |
| 父子（`SetParent`） | **是** | 命中脏 + 重绘脏 |
| 指针移动 | 不算命中脏 | **指针脏**（单列的一种） |
| 颜色 / 文字 / 透明度 / 展示倍率 / 不影响命中的装饰动效 | 否 | 只标**重绘脏** |

**集中在一个出口**：以上四类骨架变化统一走 `InkingWidget::MarkStructureChanged()`
（命中脏 + 重绘脏 + 通知场景重排，一次做完）。集中在函数里有两个好处：

1. **不会漏**——漏一个就是"这条改动没被消费"，而且往往不报错、只是画面或命中悄悄不对；
2. 将来按 §8 把标脏"送到最近的表边界"时，**只改这一处**。

**写入口负责标脏，钩子不负责**：`SetVisible` / `Resize` / `ChangeZIndex` / `SetParent`
是 `[final]` 写入口，内部统一标脏；`onVisibleChanged` / `onSizeChanged` 这些 `on*` 钩子
只挂附加逻辑（声音、动画、日志），**绝不标脏**，也绝不拦截写入口。

## 5. isDirty 的生命周期（安静帧计数）

### 5.1 为什么要有"安静帧"

标脏的语义不是"立刻去做重活"，而是**"这一帧的处理已经完成了，把账记上"**。
真正消费在帧末：`InkingScene::ConsumeFrameDirty()` 对**活跃场景**的每个节点调一次
`ConsumeDirtyFrame()`，推进这个节点自己的安静帧计数，**够数就清脏**。
顺序是"先把计数加一、再看够不够"——于是**标脏那一帧就算安静的第 1 帧**。

- **命中脏**：`kHitQuietFrames = 3`（§5 的结论是 2~3 帧足够，取 3）。
- **重绘脏**：`kRepaintQuietFrames = 5`（T-3 定的口径）。
- 重绘脏**初始为真**——第一帧总得画一次。

"连续安静 N 帧才清"而不是"标了就在帧末清"：动画期间画面每帧都在变，
如果每帧标脏、帧末又清，外部就永远观测不到"画面还在动"这个状态
（`GetRepaintingNodeCount()` 是自检断言"动效真的停了"的唯一入口）。

### 5.2 三种脏、三个消费点（别混）

| 脏 | 触发 | 消费点 | 消费做什么 |
| --- | --- | --- | --- |
| **命中脏** | 几何 / 可见性 / 层级 / 父子 | **帧首** | 重建绘制列表（`sortDrawList()`），重建后**跟着重烘命中表** |
| **指针脏** | 指针位置 / 按下状态变化 | **帧末** | 只清标记；**表不用重烘** |
| **重绘脏** | 颜色 / 文字 / 变换 | **帧末** | 记账 + 静默计时清零 |

**指针脏必须与命中脏分开**，这是 §5 单列 `isDirty` 的唯一理由：指针移动不改任何几何。
混在一起的表现是"鼠标一动就重烘整张表"（§14 里 `IsPointerDirty()` 的注释写明这一点）。

**静默 / 停放 / 关闭的场景不消费**：它们的脏标记要留着，切回来时才有意义。

### 5.3 一帧的完整账（正确顺序）

```
帧首  sortDrawList()            ← 命中脏在这里落地；表与列表同生同灭
      DispatchPointer()         ← 捕获 → 悬停 → 派发（读表 / 问动态层）
渲染  onRender(...)             ← 读重绘脏，画完不清（帧末清）
帧末  ConsumeFrameDirty()       ← 安静帧计数 +1，够数清脏；清指针脏
```

`ConsumeFrameDirty()` **不重建绘制列表**——那是帧首的事。

## 6. 命中的三态

```cpp
enum class HitKind {
    Block,        ///< 事件到此为止（半透明遮罩也属于这一类，遮挡 ≠ 未命中）
    PassThrough,  ///< 有东西，但它让过（继续往下找）
    Miss,         ///< 这里没东西
};

struct HitResult {          // 三态 + 目标，两样一起给：投递需要目标
    HitKind kind = HitKind::Miss;
    InkingWidget* target = nullptr;
    bool IsHit() const noexcept { return kind != HitKind::Miss && target != nullptr; }
};
```

**为什么要三态而不是 `bool 命中 / 不命中`**：因为"有一个不透明的面板盖在这里"和
"这里什么都没有"对上层是**两件不同的事**。前者必须终止派发（否则点击会穿透遮罩，
打到遮罩下面的按钮）；后者必须继续往下找。

`PassThrough` 的默认值是**不让过**（`Block`）还是让过，取决于组件：面板是遮挡物，
画布 / 装饰层通常让过。策略由 `_hitPassThrough` 决定——**组件只管把形状判对，
策略由写入口改、由场景合并**。

**合并只发生在同一层**（0.4.1 明确划线）：静态表内部会把 PassThrough 记下、
继续往下找 Block（`HitTable.cpp` 的 `Query`）；**跨静态 / 动态那一步不做**——
动态的 PassThrough 目前不会让给下层的静态 Block，答案仍是那个动态组件。
要做"点了穿透到下层"必须同时改 `QueryHit`（三态合并）与 `DispatchPointer`
（它现在完全不看 `HitKind`，`topmost = hit.IsHit() ? hit.target : nullptr`），
见 §15 第 1 行与 §17 第 3 条。

## 7. 动态档自判（"拉"模式）

静态组件的输入是**推结果**的：场景扫表之后调 `onPointerHover(bool)` / `onPointerPress(bool)`，
"你在不在指针下 / 按下算不算你的"这些判断都在场景那边做完。
动态组件的输入是**拉状态**的：它不进表，场景也不替它判；场景只在**指针真的变了**
的那一帧调一次 `onPointerStateChanged()`（0.4.1 T-02），它在这一趟里读
`GetPointerX()` / `GetPointerY()` / `IsPointerDown()` / `IsPointerInside()` 四个值，
**自己判命中、自己推三态**。

**第 1 条（稳定编号）**：动态组件自己维护一份**提前算好的命中状态**，而不是每帧
"问一次场景"。

**第 2 条（0.4.1 新增）**：采样时机是**指针变化的那一帧**——不是每帧，也不是每个
逻辑步。判据是 `InkingScene::_pointerDirty`（`SetPointerState` 只在位置 / down /
inside 真变时置位），所以**鼠标不动就一次都不判**。改之前是"动态组件在自己的
`Tick` 里每 20ms 判一次"，那条路既白算（没动也判）又会晚判（最多差一个逻辑步，
短于 20ms 的点击直接漏掉）。

代价是至多**一帧错位**：通知发生在帧首，组件若在通知里改了几何（例如"点了外部
就关"），本帧的命中仍按变化前的绘制列表算。这是有意接受的——要消掉它就得让
"通知"和"重建列表"分出两帧，那比一帧错位贵得多。

典型实现是 `InkingDynamicButton::JudgePointer()`：它把指针位置与自己的包络比一次，
得出 hover / pressed 两个 bool，再驱动状态机；边沿、捕获、点击三步住在
`detail::PointerProbe`（两档共用一套语义，见 §17）。之所以不回调场景：

- 场景的查询是**按表**的，动态组件不在表里，问它只能线性扫——比自判贵；
- 自判的输入是"当前这一帧的状态"，与 §11「命中与渲染同一个 t」天然一致。

**代价（必须说清）**：

- **几何遮挡已经参与**：`QueryHit` 把动态答案与静态答案按 `IsAbove` 合并，所以
  "动态组件压住下面的静态按钮"是成立的（0.4.1 实测：答案返回那个动态组件，
  `kind = Block`）。两个动态组件重叠时也按 z 序取最上面那个
  （`topmostDynamicHit` 从绘制列表尾部往前扫）。
  **不参与的只有输入归属**：动态组件仍收不到 §3 那三个推钩子，只能自判（第 2 条）。
- 动态组件在表里只留一个**洞**（`HitTable::AddHole`）：点落在洞里时，场景才去
  `topmostDynamicHit()` 现问。洞的作用是**省这一趟**，不是表达遮挡。

## 8. 生命周期成对处理

**成对**指的是：凡是"进入某个状态"，就必须有对应的"离开这个状态"的处理，
而且**离开路径可能不由你触发**。

| 成对 | 离开路径 |
| --- | --- |
| `onPointerHover(true)` | `onPointerHover(false)`（指针移出、节点被隐藏、被析构、场景切换） |
| `onPointerPress(true)` | `onPointerPress(false)`（抬起、**指针移出窗口**、窗口失焦、捕获作废） |
| `KeyDown` | `KeyUp`（松手、**切走窗口后抬起事件永远不来**，§14） |
| 键盘焦点 | 焦点转移 / 失焦 / 场景切换 |

两条硬约束：

1. **不靠"下一帧会来纠正"**。捕获作废时（指针出窗口 / 窗口失焦）必须**当场**
   把 `_pressedNode` 清成 `nullptr`，并给捕获者补一次 `onPointerHover(false)` 语义的收尾；
   否则指针会永远停在"按着"。
2. **父节点销毁时子节点的 `_parent` 会成为悬空指针**（与改造前的父链行为一致）。
   `GetChildren()` 是**视图**、不负责生命周期：子节点先销毁时自己会摘掉；
   父节点先销毁时，**子节点必须跟着销毁**（拥有型子节点由父的析构负责）。

`MarkStructureChanged()` 里的"通知场景"这一步，将来的落点是**送到最近的表边界**
（子树内的变化只在子树所在的簇重烘，不必整表重建）。现在统一走"整表脏"。

## 9. 包络分档（第三档）

命中要的是**保守包络**：宁可大一点（候选多几个），不能小一点（漏命中）。

| 档 | 用什么做包络 | 什么时候用 |
| --- | --- | --- |
| 单节点 | 形状的 AABB（含描边 / 阴影外扩） | 普通组件 |
| **子树** | 子树所有节点包络的并集（**不含滚动位移**的那一份，再取 AABB） | 容器自己当条目时（`InkingStaticPanel` 的抽屉、折叠面板） |
| 内容视口 | 容器裁剪链与画布内容视口共用的那一份（`detail/InkingGeometry.h`） | 画布 / 滚动容器 |

**第三档的意义**：容器把"整棵子树的包络"作为自己的条目，于是子孙不必各自进表
（A8a）——抽屉来回拉、内容滚动，**表一条都不变**，不需要重烘。

**抽成函数而不是各写一遍**：容器裁剪链（`AncestorClipInDevice`）与画布自己的内容视口
（A12）是同一件事的两个调用方。抄第二遍就会分叉——"画被剪的位置"和"点被剪的位置"
分家就是这么来的。

## 10. 命中表（HitTable）

形态：**簇（粗块）→ 簇内均匀格子 → CSR 候选数组**。表**不认识场景**：
它只收"条目（节点 + 包络 + 让不让过）"和"动态洞的包络"，
由 `InkingScene` 负责在帧首重建、在派发时查询。这样表可以单独被自检对账。

### 10.1 用法

```
Clear() → 逐条 AddEntry(...) / AddHole(...) → Build() → 反复 Query()
```

重建成本**正比于条目数 × 覆盖格数**，与画布面积无关。

### 10.2 格子索引 + CSR 候选

三条约束，改实现时别丢：

1. **格子只负责缩小范围**。命中与否仍由节点自己的 `HitTest` 回答，
   所以格子算粗了只是候选多几个，**不会误命中**。
2. **候选按 z 降序填**，"第一个真正包含该点的"就是最上面那个。
   全局只有一条 z 序规则（`InkingWidget::IsAbove`），和渲染顺序同源。
3. `Query(x, y, &holeHit)` 的 `holeHit` 出参：点为真时说明落在动态洞里，
   **调用方还要再去问动态层**（§7）。

### 10.3 聚类

只有**含 UI 的粗块**才建簇，每个簇用自己的 `cellSize`。
于是**建表正比于 UI 数量**，不再正比于画布面积：空白区没有簇。

### 10.4 表与绘制列表同生同灭

顺序或内容一变，候选的 z 序与包络就都过期了 ⇒ `rebuildHitTable()` 只在
`sortDrawList()` **真的重建了列表之后**调。

### 10.5 两条规则在本仓库**没有落地**（写在这里免得下一个人以为漏了）

- **没有溢出桶**（§10.5 规则 2）：那条规则是给"运行时新增的 UI 不在生成期结构里"准备的。
  本仓库的组件**构造即登记进绘制列表**，表跟着列表重建 ⇒ "新增"表现为"表脏了"，
  不是"表外还挂着条目"。
- **没有跨簇条目仲裁**（§10.5 规则 4）：那条规则是给**偏序**（存在两个条目说不清谁在上）
  准备的。我们的局部层级是**全序**（任何两个条目都可比），所以不需要。

## 11. 变换通道（表冻结、查表时反变换）

这是本设计里**最容易误解**的一节：**变换不改本地几何，也不改命中表。**

### 11.1 约定

- 变换（平移 / 旋转 / 缩放）走**独立的通道**（`dataStruct/InkingTransform.h` +
  `SetDisplayTransform` / `GetDisplayTransform`），与 `_offsetX/_offsetY`（几何偏移）
  是两件事。
- 表里存的是**保守包络**（覆盖所有可能的变换），所以变换**不在重建触发源里**。
- 查表时把查询点**反变换回本地空间**再判。这就是"表冻结"能成立的全部原因。

### 11.2 三条推论

1. **静态档照常成立**：因为不改本地几何、不改表，静态组件可以一边做过渡动画
   一边留在表里。
2. **命中与渲染必须用同一个 `t`**：过渡进度 `t` 每**渲染帧**推进一次（真实 delta，
   和画面同拍）。若命中用上一帧的 `t`，快速动画下会差帧——表现是"看着在按钮上、
   点不到"。
3. **只允许声明过的组件接受外部变换**：`AcceptsExternalTransform()` 默认 `false`，
   不声明就调 `SetDisplayTransform` 会被**拒绝并计数**
   （`GetDisplayTransformRejectedCount()`，可断言、不静默）。默认开启会让
   "某块东西莫名被挪走 / 缩放"变成难查的问题。

### 11.3 作用域

`InkingWidget` 的变换作用于**自己**；容器的 `GetSubtreeTransform()` 作用于**整棵子树**
——于是"抽屉拉出来，里面的东西跟着出来"不用每个子节点各知道一次。
子孙的绘制与裁剪都过一次**祖先仿射**（`currentAncestorAffineSlot()`，进程唯一）。

## 12. 键盘焦点

- 焦点是**场景级唯一归属**，只由场景通过 `MarkKeyboardFocus` 改。
  存两份就会出现"我以为我有焦点、场景以为我没有"。
- 组件要键盘就必须**声明**（`WantsKeyboardFocus()`）——不声明就拿不到。
  `InkingTextInput` 是典型例子：不声明就永远收不到按键。
- 键盘事件走**两条路径**（A3）：① `InkingKeyboardTarget` 的 `onKeyDown` / `onKeyUp` /
  `onTextInput` 钩子（编译期确定、零分配）；② 状态查询 `KeyboardInput::IsKeyDown`
  （跨帧状态，供"按住持续移动"这类逻辑）。
- **两条都要**：只有状态查询就做不出"按一下触发一次"（会每帧触发）；
  只有事件就做不出"按住加速"。

---

## 13. 滚动 / 裁剪与命中

- **滚动只改绘制**：滚动位移不进本地几何、不进命中表，子孙也不进表（A8a）。
  命中是**递归实时问**的，用的又是"当前子树变换" ⇒ 不用标命中脏，
  也没有表要重烘。省下的那笔白干是 A8a 选型的直接收益。
- **裁剪框跟着内容走**：内容跟着容器转、裁剪框留在原地是经典坑——
  裁剪框必须过同一条祖先仿射（与 §9 第三档同源）。
- 画布自己的内容视口（A12）与容器裁剪链共用同一份几何工具，
  **不许各写一遍**（§9）。

## 14. 指针捕获与派发细节

`_pressedNode` 是**按下时那一个节点**（捕获者），内部状态、不对外。

顺序（A4 起固定）：**先更新捕获，再据此算悬停**。倒过来的话，"抬起那一帧"
悬停还停在旧节点上。

| 情形 | 处理 |
| --- | --- |
| `justPressed` | 命中者成为 `_pressedNode`（未命中则清空） |
| 拖动中指针划过别的组件 | **不推给它们**——拖动只推给捕获者；捕获者滑出去收 `hover(false)`，滑回来再给 `hover(true)` |
| `justReleased` 且仍在捕获者内 | 派发 `onPointerPress(false)` ⇒ 触发 `onPointerClick()` |
| `justReleased` 但已离开捕获者 | 只派发"抬起"，**不触发点击**——这是用户唯一的"我反悔了" |
| 指针出窗口 / 窗口失焦 | **捕获作废**（`_pressedNode = nullptr`），补收尾（§8） |
| 回调里把命中的节点析构了 | 派发前先做**存活校准**；结构代次变过就停掉本轮（剩下的下一帧照常） |

**存活校准不是可选项**：点击回调里重建容器是常见写法，而 `_pressedNode` / `_hoveredNode`
会被 `RemoveDrawNode` 清成 `nullptr`。少了这一步就是野指针，且**只在特定点击路径下崩**。

## 15. 开放问题（本版不做）

| # | 问题 | 现状 | 出路 |
| --- | --- | --- | --- |
| **1** | **动态组件的遮挡与输入归属** | **几何遮挡已参与**（`QueryHit` 按 `IsAbove` 合并，两个动态组件重叠时也按 z 序取最上面那个）；**输入归属不参与**（动态仍收不到推钩子，由 `onPointerStateChanged` 唤起自判，见 §7 第 2 条）。**跨静态 / 动态的点击透传未实现**：动态的 `PassThrough` 不让给下层的静态 Block | 透传要同时改 `QueryHit`（三态合并）与 `DispatchPointer`（它不消费 `HitKind`），属"改派发架构"那一档，**未排期**（0.4.1 明确不做） |
| 2 | **多指针 / 多点触控** | **这一版不做**。只认**第一根按下的手指**，后来的明确忽略；`FINGER_UP` 与 `FINGER_CANCELED` 都算抬起 | 指针状态要从单值改成带 id 的表；捕获也要按 id 存 |
| 3 | **局部层级（堆叠上下文，A8b）** | 未做。`Select` 用"给自己一个高 z（默认 200）"换"展开在内容之上" | 把 `IsAbove` 换成"从根向下的 z 序列按字典序比较"；`HitTable` 里补 §10.5 规则 4 的跨簇仲裁 |
| 4 | **标脏送到最近的表边界** | 未做，统一"整表脏" | 出口已经集中在 `MarkStructureChanged()`，只改这一处 |
| 5 | **键盘的"切走再回来"** | 已处理（捕获作废 + 失焦收尾），但只覆盖窗口失焦，不覆盖输入法抢占 | 需要 IME 事件的显式建模 |

**关于第 1 条的判断依据**：动态组件存在的理由是"几何会自己变"，而"会自己变"和
"需要参与遮挡仲裁"是两件独立的需求。当前把它们捆在一起（进表 ⇔ 参与遮挡），
是因为**没有第三个调用方**需要"几何会变但又要精确遮挡"。出现这种组件时再拆。

## 17. 输入归属（0.4.1 新增）

一句话：**一个点上只有一个输入归属，而且它必须接得住这次输入。**

### 17.1 三条规则

1. **归属由命中决定，不由投递决定**。`QueryHit(x, y)` 返回的那个 Block 就是这一点
   唯一的归属；静态与动态两档对同一份几何给出同一个答案。
2. **接得住才给**。静态归属由场景**推结果**（`onPointerHover` / `onPointerPress` /
   `onPointerClick`）；动态归属由场景在**指针变化时**推一次 `onPointerStateChanged`，
   它自己读状态判（§7 第 2 条）。两档的差别只在投递方式与时机，不在"归属是谁"。
3. **容器要把答案让给子孙**。`OwnsSubtreeHit()` 为真的容器不是"答案"，它的子孙才是
   真正接住输入的那一个（`HitTestNode` 递归）。这条对静态 / 动态**同一套**
   （0.4.1 T-01：以前只有静态那一侧做，动态容器里的按钮因此"看得见、点不到"）。

### 17.2 覆盖表（谁能接住什么）

| 输入 | 静态归属 | 动态归属 |
| --- | --- | --- |
| hover / press / click | 场景推（`PushPointerHover/Press/Click`） | 自己拉（`onPointerStateChanged` 里读状态） |
| 滚轮 | 场景推（含"容器优先"，§13） | 自己读（`GetPointerWheelX/Y`） |
| 拖动 | 场景推给捕获者（`_pressedNode`） | 自己判（`PointerProbe` 的捕获语义） |
| 键盘 | 焦点节点（§12） | 焦点节点（`SetKeyboardFocus` 不区分档位） |

### 17.3 已知边界（是取舍，不是缺陷）

- **跨层的 PassThrough 不合并**：动态的"我不吃"不会让给下层的静态 Block（§6 末段）。
  要这条能力请按 §15 第 1 行评估，别在组件里绕。
- **动态的采样至多差一帧**：通知在帧首，组件若在通知里改了几何，本帧命中仍按旧列表算。
- **动态组件不进 `_pressedNode`**：场景的捕获表只记静态节点；动态的"按下之后滑出去仍算
  它按着"由 `PointerProbe` 自己维护，语义与静态档一致（同点松开才算一次 `click`）。
- **两档的边沿判定只有一份**：`detail::PointerProbe`。别在组件里再抄 `_wasDown` /
  `_captured`——第三份必然走形（`InkingButtonLike` 那次拆分就是因为这个）。
