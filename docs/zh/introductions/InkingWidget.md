# 组件：InkingWidget

**返回介绍目录：**
[介绍文档 index](index.md)

`InkingWidget` 的存在是为了回答"我在哪儿"之外的**全部**问题：我在哪棵树里、谁是我父级、我属于哪个场景、谁在我上面、我怎么画、我要不要重画、谁点得到我、我收到什么输入、我怎么排我的孩子。

它站在[锚点定位](InkingAnchor.md)之上——定位层只回答"我在哪儿"，这一层回答剩下的。而[形状](InkingShapeSpec.md)与[变换](InkingTransform.md)是它"怎么画"的两块材料。

## 三条继承线：输入是能力，不是第二套节点

`InkingWidget` 同时继承三样东西：

- `InkingAnchor`：定位；
- `InkingPointerHandler`：指针契约；
- `InkingKeyboardTarget`：键盘契约。

后两条是**可选能力**，不是"另一种节点"。多继承让任何组件天生带着这两份契约，"我要不要参与"由组件自己回答（键盘那条看 `WantsKeyboardFocus()`）。于是场景不需要"这是按钮、那是输入框"这种知识——它只认"能进树的节点"和"能推事件的接口"。

撑住这一点的是两条约束：

1. **零状态**。两个接口里一个字段都不存。焦点归属住在 Widget 上、拖动归属住在场景上——因为它们是**场景级的唯一归属**，天然要跟场景打交道，而接口不该认识场景。存两份就会出现"我以为我有焦点、场景以为我没有"。
2. **钩子即能力发现**。场景判出"谁该收这次输入"之后，直接调 `Push*`，**不做任何类型查询**。

第二条有血账：早年 `DispatchPointer` 会把任何非动态节点 `static_cast<InkingStaticButton*>` 再调 `MouseHover`——第一个不继承 Button 的可命中组件被指针扫到就是 UB。所以别在派生类或场景里加 `dynamic_cast` 的路子，那是把那个 bug 装回来。

还有一条纯工程约定：派生类重写钩子要写 `override`。漏了不是"多态失效"这么温和，而是变成**隐藏**——场景拿基类指针调，静默不生效：不报错，只是没反应。

## 按钮是语义位，不是设备位

0.5.0 之前，整条指针链路只有"一个 bool 的按下"。右键状态其实一直记着，但它到场景层就断了，到组件契约更不存在——不是少一个事件，是**少一整个维度**。

现在分 `Primary` / `Secondary` 两位。叫主/次而不是左/右，是因为单键手写笔、手柄、无障碍设备上"主/次"才是那个意思，"左/右"只是鼠标的说法。

配套的是本库对跨平台的立场：**统一输入**不是"按钮形状统一"，而是**两种输入状态在所有层同构**——同构包括事件集（press / release / click）、坐标、捕获规则。凡是只给其中一种提供能力的设计（只给左键坐标、只给左键拖动）都违背这条。

设备差异在窗口层就被吸收掉：鼠标左键 → `Primary`，右键 → `Secondary`；触摸轻点 → `Primary`，长按 → `Secondary`（转义在场景层做）。组件层永远只看到这两位，所以组件里不该出现"触摸分支"。

窗口判出的"这是手指还是鼠标"（`InkingPointerSource`）**不进入组件契约**，任何钩子都不带它。留着它只为让"设备差异被吸收"有一个明确的落点，而不是给上层留一个 `if (touch)` 的口子。

## 为什么 click 带坐标而 press 不带

几个钩子的参数形状是故意不同的，因为它们不是同一类东西：

| 钩子 | 参数 | 属于 |
| --- | --- | --- |
| `onPointerHover` | `bool` | 状态 |
| `onPointerPress` | `button, bool` | 状态转变 |
| `onPointerClick` | `button, x, y` | 事件 |

- **信号 / 状态转变**（press、`onPointerStateChanged`）回答"现在是什么状态"。它之后还能读，所以不该带参数——带了就是把持续状态抄第二份，而场景已经存了一份。
- **事件**（click、drag）回答"发生过一次什么"。发生之后状态已经变了，不带走那一刻的坐标就**永久丢失**。

`onPointerDrag` 从一开始就带坐标，click 只是跟上。

坐标是**按下点**，不是抬起点。触摸长按的锚点在按下处，手指在 slop 内微动几像素不该让菜单跟着挪；鼠标右键按下与抬起通常同点，两者无差异。

hover 只跟主键走：hover 是"我指着谁"，不是"我按着谁"。右键按住期间若让悬停消失，右键菜单一开，底下的悬停态就跟着闪。

## 光标形状：声明者与执行者

组件可以声明"指针停在我身上时，光标该长什么样"（箭头 / 手型 / I 形 / 十字）。

这个枚举放在 `input/` 而不是 `window/`，理由是归属：**声明者全是组件**（按钮、输入框、滑块），窗口层只是**执行者**。放进 `window/` 会让组件反过来依赖窗口——那是把树倒过来长。

值刻意很少。每一种都要在窗口里缓存一个 `SDL_Cursor*`，而且"多到分不清"比"少而准"更糟。要加新的就走同一条路：枚举加一项、窗口那张映射表加一行。

使用上还有一条边界：**别给容器声明**。容器的悬停目标最终是它里面的具体组件，容器自己抢着声明会让"整块面板都是手型"。窗口每帧只读当前悬停节点一次，形状不变就一个字节都不做——所以这里必须是纯查询，不许有副作用。

## 两档：几何会不会自己变

判据只有一条：**几何会不会在构造之后自己变**。

静态档构造即定型，于是能进命中表；动态档几何会自己变，不进表、每帧收到一次 Tick。这不是运行期猜出来的标记，而是**声明时就选定**的两个类型（基类不可直接实例化），所以查询与合并时不需要再问"你是不是动态的"。两档共用的东西全在基类，静态档少的**只有几何写入口**。

## 第 0 层渲染：白送一块矩形

`onRender` 在基类里是**空实现**——节点本身什么都不画。真正画第一笔的是两档各自的默认实现，都是一行 `inking_detail::FillDefaultRect`：形状取 `Rect()`、变换取单位变换、颜色取节点的 `color`。

"第 0 层"是**序号的起点，不是 z 序**。含义只有一条：组件什么都不重写时，至少能看见一块可看的色块，用来占位、对齐、看布局。子类重写 `onRender` 是把它**换掉**，不是往上叠——它不会在文字、纹理底下再垫一层底图。

合成一个 `detail` 函数而不是两档各写一份，是因为两档是**兄弟**（都直接继承 `InkingWidget`）：静态版不是动态版的基类，拆成两个实现文件之后匿名 `namespace` 也不再共享。合起来之后，抗锯齿、展示倍率换算、顶点缓存、祖先仿射全走同一条 `fillShape`，"按钮走一条路、默认矩形走另一条路"这种事才不会发生。

两个边界：

- **容器不经过它**。Panel 这类自己铺底，还要接描边、裁剪、滚动；第 0 层只服务于"没有自己画法"的叶子；
- **阴影不能挪到装饰笔**。阴影是"形状之下的偏移副本"，必须跟填充同一趟；放进装饰遍反而会盖住自己的内容。

## 一笔不够：装饰笔画在子树之上

`onRender` 是**自己**这一笔，落在整棵子树之前——祖先先画，子节点自然压在容器上。于是"描边"跟着填充走会被子节点盖住，加完等于没加。

第二笔是 `onRenderDecoration`：时机是**本节点整棵子树画完之后、上层兄弟画之前**。描边这类"要压在子孙之上、又不该越界压到层级更高的兄弟"的一笔，只有这个位置放得对。

它不靠"全局再遍历一趟"，靠的是绘制列表的一个性质：列表按（z, 注册序）的字典序排，等价 DFS 先序，所以**每棵子树在列表里是连续一段**。遍历时把有装饰笔的节点压进待落栈，发现当前节点已经不在它的子树里，就先落笔。全局第二趟不行——那会让描边压到上层兄弟头上。

三条契约：装饰笔**不参与命中、不进绘制列表、不标脏**，它和 `onRender` 同帧提交。默认 `HasRenderDecoration()` 为 `false`，所以"每帧多一趟"的稳态成本只是一次布尔虚调用，而不是给每个节点再搭一遍渲染槽位。

传进这两个钩子的坐标都是**设备像素**（展示倍率已乘过）下的节点绝对左上角；祖先的子树变换挂在渲染槽里，组件侧一个字不用改。

## 代价

多继承不是白拿的：接口不能有状态，所以凡是需要知道场景的东西都得留在 Widget 上，接口只放纯行为。这条约束反过来是好事——它逼着"这个能力要不要跟场景打交道"在设计时就有一个答案。
