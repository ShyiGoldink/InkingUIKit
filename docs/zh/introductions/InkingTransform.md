# 变换：InkingTransform

**返回介绍目录：**
[介绍文档 index](index.md)

`InkingTransform` 的存在是为了给"看起来在哪儿、有多大、朝哪边"一条独立的通道：平移、旋转、缩放。

它最重要的一条性质不在自己身上，而在它**不是布局**。这条分界线画在哪里，决定了后面所有的取舍。

## 一条通道，两种代价

本项目把"东西变了"分成两类：

| 通道 | 内容 | 代价 |
| --- | --- | --- |
| **变换通道** | `translateX/Y`、`rotate`、`scale` | **不动命中表** |
| **布局通道** | 宽高、会引发兄弟重排的定位 | 必须**重烘**受影响的子树 |

差别来自命中表怎么烘：表按**本地几何**烘，查询时把指针的点**反变换**回本地空间。于是"组件的几何"和"组件现在被摆成什么样"彻底解耦——变换改的是后者，表里那份前者一个字节没动，表自然还有效。

收益很具体：**静态组件也能有变换**。否则"能旋转"就等于"必须进动态档"，而动态档要付每帧 Tick、不进命中表的代价。

代价同样具体：**每查一次命中，多一次反变换**（几个乘加）。这是刻意换来的——几次浮点运算，换"静态档也能转"。

## 它为什么不叫几何写入口

变换不碰本地几何：形状、尺寸、锚点、偏移，一个字节都不动，只改"画在哪儿、画多大"。

所以静态档那条铁律（构造之后没有几何写入口）没有被破坏。反过来说，它也就**不改变占位**：兄弟不让位，布局与滚动范围都不认它。

想把别人推开，那是布局通道的事。指望变换去挤开邻居，只会得到一个"看着错位、点着也错位"的界面，而且错得很隐蔽。

## 原点取组件中心

形状都是按**左上角**定义的，绕左上角转起来不是直觉里的样子：一个 200×100 的按钮转 90°，会整个跑到左边去。

所以原点取**组件中心**，等价 CSS 的 `transform-origin: 50% 50%`。这条是**约定**而不是实现：变换函数只接受一个中心点参数，它不认识组件，也不替你算中心——算中心是调用方的事，只有组件自己知道自己的尺寸。

## 度，顺时针为正

`rotate` 的单位是度。屏幕坐标 y 向下，所以**顺时针为正**，`0` 指向正右方。

理由和 CSS 一样：配置里写 `15` 比写 `0.2618` 直观。这套口径和[形状](InkingShapeSpec.md)里的角度是同一套，两处用的是同一行换算。

## 正反两个方向必须挨着写

正向用于绘制（本地 → 屏幕），反向用于命中（屏幕 → 本地）。两者必须**严格互逆**，否则就回到"画的是一个、点的是另一个"那条老路。

所以它们在同一份文件里紧挨着，而不是各写各的。分开写就一定会漂：某天有人只给其中一边加了偏移，另一边没跟上，而这种错只在特定角度、特定位置露头。

实现上有一个必须处理的退化：`scale == 0` 时逆变换不存在。配置阶段的 0 会被拦住；真漏到运行期就按 `1` 处理——宁可不命中，也不要除零得到 `inf` 之后到处乱命中。

## 插值不做短路径

角度直接线性插。所以从 350° 过渡到 10° 会**倒着绕 340°**，不会"聪明地"正着走 20°。

看起来不够聪明，但这是对的：使用者写的是**角度数值**，不是"转过去"这个动作。真做了短路径优化，插值轨迹就不再由输入决定，出了问题也无从复现。要走近路就把目标写成 `370`——显式、可预测。

## 已知的边界

诚实列一下：

- **只有一个 `scale`**：不做轴分离的 `scaleX` / `scaleY`。需要拉伸的场合目前没有口子，这是刻意的简化；
- **负的 `scale` 等于镜像**：允许，但很少用，它会让"旋转方向"的手感变得反直觉；
- **多层复合不在这一层**：一次变换写不成"父变换 ∘ 子变换"。那件事在 `InkingAffine` 里，它依赖本文件；
- **运行期随便改变换要动命中表**：表里登记的是"所有可能变换的并集"，而任意拖动是**无界**的、并集算不出来。所以运行期那条显示变换（`SetDisplayTransform`）是框架里唯一会触发整表重烘的显示通道，见[组件](InkingWidget.md)。
