# 形状：InkingShapeSpec

**返回介绍目录：**
[介绍文档 index](index.md)

`InkingShapeSpec` 的存在是为了给项目中的每个组件回答一个问题：**它的轮廓长什么样**。

答案只有一份，却要同时喂给三件互相看不见的事——画出来、点得到、算包围盒。这个"一份定义、三处派生"的选择，几乎决定了它全部的形态。

## 核心结构：一种假反射

它的核心是一份"**把可能会用到的字段全放在一起**"的结构体，外加一个 `kind` 说明当前是哪一种形状。

这在 C++ 里通常对应 `std::variant` 或虚函数表，这里两个都没用，理由有两条：

- **不需要运行期分派的开销**。形状在配置里就是写死的，运行期只想知道"这一个属于哪一类"，一次 `switch` 就够；
- **不需要真正的反射**。生成器在编译期按 `type` 查表，直接展开成这个结构体的字面构造，运行期根本不存在"解析字段名"这一步。

好处是显然的：零查表、零分配、可以整份拷贝，也不需要为了两三个参数引入一层多态。

代价也同样明确，而且更值得注意：

1. **用不到的字段照样占内存**。绝对值不大，但结构体因此变大，缓存行利用率和拷贝成本都受影响——所以字面量的类型要选得更克制（`kind`、`cap` 用 `std::uint8_t`，而不是默认的 `int` 枚举）；
2. **字段全都有默认值**，于是"写了但没生效"和"没写"看起来一模一样。这是本项目最常见的一类错误来源。

## 为什么必须一条定义派生三件事

如果渲染一套逻辑、命中一套逻辑、包围盒再算一遍，就一定会出现这种情况：

> 画出来是圆角，点到的却是直角。

两边单独看都是对的，合起来才错，而且只在某些位置露头——极难排查。

所以这里用的是 **SDF（带符号距离场）**：形状被定义成"平面上每一点到边界的带符号距离"这一个函数。符号取通用约定：

- `f < 0` 在内部、`f = 0` 在边界、`f > 0` 在外部；
- 裁剪 = 保留 `f <= 0` 的区域。

于是三个派生量都是同一个函数的直接后果，而不是三份独立的实现：

| 派生量 | 用途 |
| --- | --- |
| 带符号距离 | 渲染（填充 / 描边 / 裁剪） |
| 距离是否 `<= 0` | 命中（这个点在不在形状里） |
| 由形状推出的外接矩形 | AABB（命中表按格子登记） |

顺带还白捡了两件事：抗锯齿就是标准的 `smoothstep(-aa, aa, d)`，不需要额外的边缘判定；`abs(d)` 天然就是"到边界的距离"，描边、外发光这类效果不用再写一遍几何。

## 为什么坐标基准是组件左上角

形状不带自己的位置，只描述"在一个 `width × height` 的框里怎么长"，坐标原点是**组件左上角**，单位是**设计坐标**。

这一点和[锚点定位](InkingAnchor.md)是同一个前提：InkingUIKit 是 LetterBox 式的，窗口缩放只改倍率、不改逻辑坐标。所以一个形状按设计坐标定下来，在任何窗口尺寸下都成立——换分辨率、拉窗口，形状不用重算。

也因此，形状本身**不参与布局**：它只是一个纯函数，问它一次答一次，不持有任何状态。

## 为什么只有"属于它的那几个参数"生效

`kind` 决定读哪些字段，其余字段存在但被忽略。这带来两个必须记住的语义：

- **尺寸语义由形状自己决定，不能一律按 `width × height` 理解**。圆和正多边形取的是 `min(w,h)` 并且居中，所以 100×60 的组件画圆得到的是居中、直径 60 的圆，不是椭圆；线段只有横向用满，纵向居中；
- **同名参数在不同形状里可能没意义**。`rotation` 对多边形是第一个顶点的方向、对星形是第一个外角的方向；`thickness` 对圆环是环宽、对线段是线宽。写法相同，读法靠 `kind`。

这是"假反射"最直接的账单：结构体不替你检查语义，**调用方负责确认自己填的字段真的会被读到**。工厂函数（`RoundedRect(radius)` 这类）存在的意义就是把这份对应关系固定下来，让"填错字段"变成编译期就能发现的事。

## 角度：度数、顺时针为正、不做短路径

角度一律用**度**，屏幕坐标 y 向下，所以**顺时针为正**，`0` 表示 `+x` 正右方。

这与变换层的 `rotate` 保持同一套口径——配置里写 `15` 比写 `0.2618` 直观得多。

另一条是刻意的：**不做短路径转换**。比如从 270° 转到 0°，不会帮你顺时针补到 360°（等价于 0°），而是按你写的数逆时针转回去。

看起来不够"聪明"，但这是对的：使用者写的是**角度数值**，不是"转过去"这个动作。真做了短路径优化，插值动画的中间轨迹就不再由输入决定，出了问题也无从复现。要短路径就让调用方自己算——这是显式的、可预测的。

## 校验的两种态度

参数不是"能填就收"，但也不是一律报错。判据是**这条约束属于谁**：

- **配置错误** → 断言当场拦下。负半径、`sides < 3`、环宽 `<= 0` 都属于"写错了"，自动修好只会把错误藏到画面里。debug 下直接断在工厂函数上，release 下兜底修正成正数；
- **形状自身的数学要求** → 夹取，不报错。圆角半径不能超过 `min(w,h)/2`、环宽不能超过外半径、超椭圆指数太大 `pow` 会溢出——这些不是使用者写错，而是形状在边界上会退化，夹住才是唯一合理的处理。

两类混在一起就会两头不讨好：该断的不停，不该断的把合法配置也拦了。

还有一条与形状无关、但同样容易踩的：**顶点表是借用的，不拥有**。生成器烘的是文件作用域的静态数组，活得比任何组件都长；手写时却要自己保证这块内存不被提前释放——拷了 `InkingShapeSpec` 的组件会一直拿着那个指针。

## 已知的局限

诚实列一下，避免被"精确"这个词误导：

- **椭圆与超椭圆的距离是近似值**。它们没有初等闭式的最近点，这里保证的是**符号精确**（内外判定永远对）、距离在边缘附近够准。要拿这个距离做远场效果（大范围外发光）时会露馅；
- **圆弧的包围盒是保守的**。整个弧带落在外径圆里，按实际角度范围算能更紧，但那段代码只为省几个格子，不值当；
- **形状种类是封闭的**。要新形状得改这个头文件和渲染侧，没有"注入自定义 SDF"的口子——这是刻意的：命中与渲染必须同源，开放注入点就等于重新打开"画的和点的不一致"那道门。
